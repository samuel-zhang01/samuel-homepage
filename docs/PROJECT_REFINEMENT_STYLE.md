# Project refinement direction

This pass helps a visitor understand what Samuel built, why he built it, and what to do in the demo. Existing System 7 typography, canonical icons, paper colours, bevelled controls and hard window shadows remain the design language.

## Visitor journey

1. Name the thing and its useful outcome in the title and summary. A Mac app introduction describes what a person can do with it; framework names belong later.
2. Explain the work in Samuel's first person: **What I built** and **Why I built it**. Use a concrete problem, action and outcome rather than an abstract list of capabilities.
3. Offer a purposeful interaction: **Try it** gives a short action and tells the visitor what the result means. Instructions should appear before the controls on phones too.
4. Offer **How it works** as a secondary disclosure after the visitor understands the point. Keep scientific distinctions and important numerical findings, with enough plain language to interpret them. Purpose, contribution and demo instructions remain visible.
5. Put repositories, presentations, reports, downloads and technical metadata after the explanation. Give each link a useful name. They are things to read or use, not proof of authorship.

Generic development phases no longer appear in the shared project introduction. Audience labels, repeated demo labels and internal audit terminology should not crowd the first screen. Keep qualification beside the result it affects: distinguish a recorded experimental result from a browser calculation or sample without repeating a warning throughout the page.

## Copy

Samuel is the sole author. Use **I**, **my** and active verbs for his work; use **you** for visitor instructions. Do not invent collaborative authorship. Keep claims within the supplied repositories, reports, thesis, presentations and results. Original source filenames, figures and scientific identifiers can remain where they aid understanding; never publish private local paths.

Translate all new interface and explanatory copy in en-GB, en-US, zh-CN and zh-TW using the existing project translation workflow. Preserve original scientific figures, equations and source code.

## UI

Use one-pixel rules and readable white/warm paper for explanation; avoid wrapping every paragraph in a raised panel. Keep grey window furniture, neutral bevelled action buttons and navy links/selection. Scientific colour is reserved for a meaningful series, instrument state or outcome. Use existing 15px prose, 18px section headings and 22px document titles. Reflow narrow content; preserve 44px phone controls and the canonical 16/32/48px icons.

## Visitor review gate

An adversarial reviewer should be able to answer, without opening a repository:

- What did Samuel make or investigate?
- What real problem is he addressing?
- What should I try, and why?
- What changes when I try it, and what does that mean?
- What belongs to the original work, and what is this browser demonstration doing?
- Where can I use, download or read more about it?

The user's target is at least 9/10 for this comprehension review. Record observed issues and repairs; do not substitute source checks for an actual browser visit.

## Shared UI changes

The shared project introduction presents purpose and contribution before methods. It removes the generic **Development** timeline and the repeated objective paragraph, places the guided demo before the optional **How it works** disclosure, and moves source links and tool metadata below the explanation. Download links remain beside the primary demo action. Demo chrome keeps purpose, a concrete action and an outcome cue ahead of the controls at every viewport size.
