---

The highest-priority issue is silent loss of edits between browser tabs. Project demos also lose their state when another desktop window opens. The mobile project toolbar takes more than half of the available reading pane at 320px. Fix these before spending time on cosmetic copy changes.

This report contains seven confirmed issues and nine editorial or information-design recommendations. Four confirmed issues were introduced by the latest commit; three already existed. The recommendations are separate from regression findings.

The working tree was clean when the review started. Local `main` was ten commits behind the already-configured `origin/main`. This is a review of the local revision above, not the newer remote branch or the deployed website. No application code was changed.

## Confirmed issues, ordered by priority

### F1. [P1] Preserve pending edits when another tab saves

Location: [src/components/ProductivityApps.tsx:539](../src/components/ProductivityApps.tsx#L539). Related code: [debounced save:509](../src/components/ProductivityApps.tsx#L509), [storage listener:550](../src/components/ProductivityApps.tsx#L550), and [ProductivityExtras.tsx:86](../src/components/ProductivityExtras.tsx#L86).

Existing defect. Reproduced in Chromium with two Note Pad tabs on the same origin. A storage event replaces the entire local notebook, even when that tab has a newer unsaved edit. The replacement also cancels the pending save through the effect cleanup. Both tabs then display the older text with a saved status.

Reproduction:

1. Open `/en-gb/desk` in two tabs and open Note Pad in both.
2. Enter `TAB A DRAFT` in the first tab.
3. Before its 180ms autosave delay finishes, enter `TAB B NEWER DRAFT` in the second tab.
4. Wait for autosave.

Observed values:

| Moment | Tab A | Tab B | Stored notebook |
| --- | --- | --- | --- |
| Immediately after typing | `TAB A DRAFT` | `TAB B NEWER DRAFT` | Save pending |
| After saves settle | `TAB A DRAFT` | `TAB A DRAFT` | `TAB A DRAFT` |

Change: track local dirty state and the revision from which an edit started. Do not replace a dirty editor with an incoming snapshot. Preserve both versions and offer a conflict choice, or merge independent page edits with a coordinated revision check. Apply the same policy to the shared persistence hook: it also loads incoming values unconditionally and writes a whole object after 180ms. Simply changing the debounce delay will not resolve the race.

Acceptance check: simultaneous edits to the same page retain both drafts or present a conflict. Edits to different pages survive together. Repeat for Quick List and calendar notes, and include close/unload flushing in the test. The browser reproduction here covered Note Pad; the other apps share the unsafe pattern but were not individually reproduced.

### F2. [P2] Keep demo state when desktop focus changes

Location: [src/components/projects/ProjectDocument.tsx:63](../src/components/projects/ProjectDocument.tsx#L63). Related mount condition: [line 121](../src/components/projects/ProjectDocument.tsx#L121).

Regression in `a60ee8e`. The effect treats an inactive embedded project as a closed demo. Opening Pocket Calendar from the menu clock unmounts the current demo and discards its state, even though the visitor never used the close command. The displayed warning only describes closing the demo.

Reproduction: open `/en-gb/projects?view=files`, select CV Keyword Automator, open its demo, and replace the sample CV text. Open Pocket Calendar with the menu clock, close the calendar, and reopen the demo. The edited text has been replaced by the original fictional sample. The experiment element disappears as soon as the calendar opens.

Change: separate focus, visibility and lifetime. Keep the demo mounted when another window gains focus; pause its timers or rendering through an activity signal. Reserve disposal for an explicit close/reset action. If components must be unmounted, retain their state outside the mounted demo. Removing only the effect is insufficient because the `active` condition also unmounts it.

Acceptance check: edit the CV, open and close another accessory, and confirm that both the draft and selected demo tab survive. Repeat after resizing across the 760px layout boundary. Explicitly closing the demo may still reset it according to its stated behavior.

## Copy issues and proposed changes

This is an audit with suggested replacements, not an in-place rewrite. The avoidance skill's technical/docs allowances were applied to scientific explanations and its general prose guidance to the portfolio introductions. The comments below assess clarity and reading experience, not authorship.

No P0 writing artifacts were found in the sampled public entry copy. No clear Tier 1A vocabulary cluster was found there. No separate Tier 1B wordiness finding is warranted in that sample. Terms such as “doubly robust,” “conformational landscape” and “robustness” have specific technical meanings and should remain. The main issues are repetition, abstract product language and unclear labels.

### C1. [P2 copy] Remove development lists that repeat the feature description

Where: [src/data/projects.ts:115](../src/data/projects.ts#L115), [line 127](../src/data/projects.ts#L127), [line 139](../src/data/projects.ts#L139), and the shared renderer at [ProjectCaseBrief.tsx:35](../src/components/projects/ProjectCaseBrief.tsx#L35).

Example: Note Pad repeats “eight” pages in its introduction, development list and capabilities. “Create a small ruled notebook,” “Add eight persistent pages” and “Support text export” read as a generic build checklist rather than an account of decisions or results. Sketch Pad and Quick List repeat the same three-step shape.

Assessment: clear low-information repetition. The pattern is more significant than any individual word. Utility pages do not need the same case-study structure as a research project.

Suggested compact version: “Eight ruled pages save notes in this browser. Insert the date, export a text copy, or include the notebook in a Desk Accessories backup.” Remove the duplicate development/results blocks for this utility. Retain a development section only when it adds a specific constraint, decision or observed result already supported by the source.

### C2. [P2 copy] Put the contribution ahead of repeated purpose statements

Where: [ProjectCaseBrief.tsx:28](../src/components/projects/ProjectCaseBrief.tsx#L28), [projectStories.ts:24](../src/components/projects/projectStories.ts#L24), and [projects.ts:288](../src/data/projects.ts#L288).

Example: CV Keyword Automator describes extraction and templates in its summary, detail, objective, contribution and development list. Meanwhile, “Samuel’s contribution” is collapsed. The most useful portfolio distinction, what Samuel built and what the browser demonstration adds, is harder to find than the repeated purpose.

Assessment: clear repetition; the proposed hierarchy is an editorial recommendation. Show the short contribution by default and make extended implementation notes optional.

Suggested opening from the existing record: “Samuel built a Python workflow that extracts job requirements, selects a pre-authored CV template and compiles a PDF with LaTeX. The browser demo uses fictional text to show which suggested changes the sample CV supports.” Follow with the existing limitation and one exercise. Do not repeat the same workflow under three more headings.

### C3. [P2 copy] Explain COVERD without “intelligence layer” language

Where: [projects.ts:219](../src/data/projects.ts#L219), [projectStories.ts:237](../src/components/projects/projectStories.ts#L237), and [SystemSevenDesktop.tsx:946](../src/components/SystemSevenDesktop.tsx#L946).

Quoted spans: “An ATS-connected recruitment intelligence layer” and “Recruiters reviewing applications across specialist evidence dimensions.” These phrases require a reader to decode several abstractions before learning the task.

Assessment: clear clarity issue, not a Tier 1A authorship signal. Expand ATS once and describe the action.

Suggested summary: “COVERD reviews applications from an applicant tracking system and gives recruiters a shortlist with supporting reasons. Recruiters make the final decision.” Suggested audience: “Recruiters reviewing job applications.” The existing description of six separate review areas can follow this introduction.

### C4. [P2 copy] Replace the generic trust statement with observable behavior

Where: [SystemSevenDesktop.tsx:1073](../src/components/SystemSevenDesktop.tsx#L1073).

Quote: “Trust comes from evidence, visible uncertainty, candidate agency and accountable human decisions.” This broad maxim introduces abstract virtues already repeated in the surrounding product copy. It does not tell the reader what they can inspect or do.

Assessment: judgment call as a slogan; weak explanatory copy in this location. Replace it with the concrete behavior already described nearby: “Recruiters can inspect the evidence behind each assessment and review uncertain cases before deciding.” Keep candidate agency as a claim only where the page explains the candidate's actual controls.

### C5. [P2 copy] Remove the unquantified cost-saving endorsement

Where: [SystemSevenDesktop.tsx:2060](../src/components/SystemSevenDesktop.tsx#L2060).

Quote: “avoids substantial hosted-runner costs.” The adjective supplies the magnitude, but the page provides no comparison or period. This is an evidence gap, not a claim that the saving is false.

Assessment: definite cut unless the owner can supply a checked comparison. Suggested version: “Runs CI jobs on Samuel’s hardware across different CPU architectures.” If a cost result is added, give its period, basis and source; do not invent a number to make the sentence sound specific.

### C6. [P2 copy] Call the local demonstrations “interactive demos”

Where: [ProjectDocument.tsx:32](../src/components/projects/ProjectDocument.tsx#L32), [line 97](../src/components/projects/ProjectDocument.tsx#L97).

Quoted labels: “Open live demo” and “Go to live demo.” Several demos use fictional data, deterministic rules or saved scientific results. Their own explanations disclose this, but “live” can suggest an operating backend or fresh model inference.

Assessment: a terminology judgment call with a simple fix. Use “Open interactive demo” and “Return to demo.” Keep “Visit website” for an external product, and name saved results as saved results. Do not remove the scientific or fictional-data explanations.

### C7. [P2 copy] Describe browser storage precisely

Where: [ProductivityApps.tsx:393](../src/components/ProductivityApps.tsx#L393) and [line 398](../src/components/ProductivityApps.tsx#L398).

Quotes: “nothing is uploaded or synced” and “Local autosave is on.” The first conflates cloud sync with the cross-tab synchronization that the app implements. The second is unconditional even though individual accessories can report unavailable storage.

Assessment: clear scope ambiguity. Suggested introductory copy: “Notes, drawings and plans are saved in this browser. There is no cloud backup; export a backup to move them.” Use “Saved in this browser” for the general feature label, or derive an autosave status from a storage check. Do not claim successful persistence when a write has failed.

### C8. [P2 copy] Replace stacked utility slogans where the action is unclear

Where: [ProductivityExtras.tsx:737](../src/components/ProductivityExtras.tsx#L737), [line 861](../src/components/ProductivityExtras.tsx#L861), [line 1197](../src/components/ProductivityExtras.tsx#L1197).

Quotes: “One quiet place for the day ahead” and “Pick boldly. Check responsibly.” Both could introduce unrelated products. The colour slogan provides no useful instruction until the reader inspects the controls.

Assessment: optional editorial improvement. A little playful writing fits this desktop; it need not be removed everywhere. At the calendar, use “Choose a date and add a note.” At Colour Studio, use “Compare text and background colours.” Preserve specific playful lines such as Snake's “become inconveniently long,” which describe the game and have a distinct voice.

### C9. [P2 copy] Label the status of product capabilities before repeating them

Where: [SystemSevenDesktop.tsx:943](../src/components/SystemSevenDesktop.tsx#L943), [line 1006](../src/components/SystemSevenDesktop.tsx#L1006), [line 1038](../src/components/SystemSevenDesktop.tsx#L1038), and [line 1054](../src/components/SystemSevenDesktop.tsx#L1054).

The COVERD page repeats application review, supporting reasons and recruiter control in its opening, thesis, feature grid and process diagram. It also presents “Outcome Learning” in the same tense and visual treatment as ATS connection and voice interviews. The page does not tell a visitor which capabilities are available, prototypes or plans.

Assessment: the missing distinction is clear; the actual capability statuses need confirmation from the owner or a product record. Do not infer them from the portfolio prose. Keep one short product explanation and the process diagram, then add verified capability statuses and any available evidence. Remove feature cards that add no information beyond the diagram. This reduces repetition without inventing customer outcomes or shipping claims.
